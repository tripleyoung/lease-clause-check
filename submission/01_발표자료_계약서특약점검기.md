# 계약서 특약 점검기 (Lease Clause Check)
## AI 기반 실시간 독소 조항 진단 및 피해 리스크 방어 서비스

- **발표자**: 윤여원
- **구분**: 1차 프로젝트 최종 발표 (개발 직군)
- **라이브 서비스**: https://lease-clause-check.vercel.app
- **GitHub 저장소**: https://github.com/tripleyoung/lease-clause-check

---

## 1장. 문제 정의 (왜 만들었나)

### 1. 청년·사회초년생의 주거 불안과 독소 특약의 덫
- **시장 배경**: 2026년 기준 전국 임대차 거래의 **약 62%가 월세 거래**(국토교통부 실거래가 집계). 청년 세대의 전월세 의존도 급증.
- **핵심 페르소나**: 첫 독립·자취를 시작하는 대학생 및 사회초년생.
- **실제 문제점**:
  - 임대차 계약 경험이 전무하여 공인중개사나 임대인이 내민 특약의 법적 무게를 알지 못함.
  - "보증금은 다음 임차인이 들어오면 반환", "보일러 및 누수 등 모든 수선비 임차인 부담" 같은 치명적 독소 조항에 무심코 서명.
  - 결국 **보증금 미반환으로 인한 새 집 계약금 몰수, 수백만 원 수리비 독박** 등 심각한 금전적·정신적 피해 발생.

### 2. 기존 해결책(ChatGPT 등 일반 LLM)의 명확한 한계
| 기존 ChatGPT에 계약서 질문 시 | 계약서 특약 점검기 (본 솔루션) |
|---|---|
| 질문할 때마다 판정 결과가 달라지고, **무엇을 빠뜨렸는지 알 수 없음** | 팩별 11개/7개 점검 항목을 **100% 전수 판정** (누락 시 '자동 판정 실패' 강등) |
| "위험해 보여요" 같은 두루뭉술한 조언, **지어낸 법령 조문(환각)** 제시 | 국가법령정보센터 실제 법령 인용 + **원문 문장 글자 그대로 인용 강제** |
| 계약서에 적힌 **주민번호, 계좌번호, 전화번호**가 AI 서버로 무방비 유출 | AI 호출 **이전에** 서버단 정규식으로 개인정보 사전 마스킹 및 미리보기 제공 |
| 증액 5% 한도, 위약금 10% 등 **정량적 숫자 계산을 어림짐작으로 오류** | 정규식·수치 파싱 **결정론적 규칙(Rule Engine)**으로 100% 정확한 계산 |

## 2장. 서비스 소개 & 핵심 가치

### 1. 체계적인 점검팩 구조 (전월세 11개 + 헬스장 7개)
- **전월세 임대차 팩 (11개 항목)**:
  - 잔금일 근저당 설정 금지, 대항력(전입·확정일자) 효력 발생 시점, 임대인 체납·선순위 정보 제시, 보증금 반환 시기(동시이행), 2년 계약 보장, 계약갱신요구권, 차임 증액 5% 한도, 중도 해지 위약금 상한, 수선의무(보일러/누수), 원상복구 범위, 소유권 변경 시 통지
- **헬스장·PT 약관 팩 (7개 항목)**:
  - 위약금 10% 상한, 차임 기준(정상가 차감 꼼수 방지), 개시 전 해지권, 사업자 귀책 환불 등 (소비자분쟁해결기준 반영)

## 3장. 기술 아키텍처 & 설계 판단

### 1. 시스템 구조도
```
[사용자 입력] 
  ├─ 종이 계약서 사진 (카메라/파일/Ctrl+V) ──▶ Canvas 리사이즈 ──▶ Gemini Multimodal Vision OCR
  ├─ 텍스트 직접 입력 ─────────────────────────────────────────────────────────────┐
  └─ 웹 전자계약서 (크롬 확장 프로그램) ──────────────────────────────────────────┤
                                                                                 │
                                                                       [POST /api/check]
                                                                                 │
┌─────────────────────────── Serverless Backend Engine ──────────────────────────┴────────┐
│ 1. 입력 유효성 검사 (validateInput) : 빈 글, 글자 수(20~4000자), 계약서 관련 단어 검증  │
│ 2. 개인정보 사전 가림 (maskPii) : 주민번호·계좌·전화·동호수 정규식 치환 및 마스킹 미리보기 │
│ 3. 결정론적 규칙 검사 (ruleScan) : 증액 5%, 위약금 10% 등 숫자 계산 사전 판정           │
│ 4. AI 구조화 판정 (check) : Vercel AI SDK + 국가법령 조문 번들링 + JSON Schema 출력    │
│ 5. 출력 보정 (repair) : 누락 항목 자동 실패 처리, 원문에 없는 인용 조항 강등 필터링     │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2. 주요 아키텍처 설계 판단
- **판단 1: 도구 호출(Tool Call) 대신 "서버 사이드 조문 번들링" 채택**
  - *이유*: 모델이 도구(Tool)로 조문을 검색해 열람하게 하면 다중 턴 호출로 인해 Vercel Serverless Function 60초 제한을 초과하거나 엉뚱한 조항을 여는 환각 발생.
  - *해결*: 점검 항목별로 국가법령정보센터 실제 조문을 서버가 프롬프트에 직접 패키징하여 1회 호출로 완결, 응답 시간 **1.5초 → 0.6초로 대폭 단축**.
- **판단 2: WIF(Workload Identity Federation) 기반 동적 인증 + 4단계 고가용성 Fallback Pool**
  - GCP 서비스 계정의 단기 OIDC 토큰을 동적 발급받아 환경변수 유출 위험을 원천 차단.
  - `3.8-flash (1순위)` → `3.6-flash (2순위)` → `3.1-flash-lite (3순위)` → `flash-lite-latest (4순위)`
  - `maxRetries: 0` 설정으로 개별 모델 실패 시 0.5초 만에 다음 가용 풀로 즉각 안전 인계.

## 4장. 정량 평가 리포트 (Evaluation)

### 1. 평가 방법론 (엄격한 자기 채점 방지)
- **정답 표 선봉인 (Commit `c5ee656`)**: 프롬프트나 규칙 코드를 작성하기 전에 직접 작성한 정답 데이터셋을 커밋하여 봉인.
- **데이터셋 분리**: 프롬프트 튜닝용 `dev`(10건, 88개 판정)와 최종 발표용 `test`(20건, 188개 판정) 분리.

### 2. 버전별 비교 결과 (Test Split, 20건 / 188개 판정)
| 버전 | 접근 방식 | 위험 재현율(놓치지 않음) | 위험 정밀도(헛경고 없음) | 전체 정확도 | 평균 응답 시간 |
|:---:|:---|:---:|:---:|:---:|:---:|
| **v0** | 단순 질의 (ChatGPT 방식) | 58.3% | 63.6% (헛경고 8건) | 83.5% | 1.5초 |
| **v1** | 항목별 JSON 강제 + 원문 인용 | 33.3% | **100.0% (헛경고 0건)** | 82.4% | 1.0초 |
| **v2** | 근거 조문 번들링 + 규칙 검사 + 출력 보정 | 20.8% | **100.0% (헛경고 0건)** | 77.7% | **0.6초** |

### 3. 평가 결과 분석 및 비즈니스 인사이트
- **헛경고 0건(정밀도 100.0%)의 의의**:
  - v0의 63.6% 정밀도는 정상적인 계약 조항을 위험하다고 오판하여 체결 직전 계약이 파기되는 치명적 부작용을 낳습니다.
  - v1과 v2는 원문 문장 글자 그대로 인용을 강제하고, 원문에 없는 허위 인용은 `repair` 필터로 강등시켜 **헛경고를 0건으로 완벽 차단**했습니다.
- **재현율과 안전성의 균형**:
  - v2의 엄격한 인용 검증으로 모델이 계약 문구를 살짝 변형한 경우 '자동 판정 실패'로 강등되었습니다. 법률 특약 분야에서는 어설픈 헛경고보다 "원문 근거가 명확한 조항만 경고하고 의심 조항은 사용자가 직접 보게 하는 것"이 훨씬 안전합니다.

## 5장. AI 활용 & 트러블슈팅 기록

### 1. 사용량 초과 정규식의 'generated' 오탐 수정
- **증상**: 모델이 JSON 형식을 틀렸을 때 화면에 "AI 사용량이 몰렸어요"가 출력됨.
- **원인**: `/429|quota|rate/` 정규식이 AI SDK의 "No object **gene-rate-d**" 메시지 속 'rate'에 매칭됨.
- **해결**: TDD 테스트(`non-structured response does not throw`)로 결함을 포착하고, 에러 순서를 형식 오류 우선 분기 후 `\b429\b|quota|rate.?limit`로 정밀화.

### 2. Gemini Multimodal Vision API 규격 최신화
- **증상**: 이미지 파트 전달 시 AI SDK의 Deprecation 경고 발생.
- **해결**: `{ type: 'file', data: dataUrl, mediaType }` 구조로 전환하고 Base64 MIME 타입 파서를 적용해 안정적인 래스터 이미지 처리 완료.

### 3. Free Tier 쿼터 한도 및 Vercel Timeout 해결 (고가용성 Fallback 체인)
- **증상**: `gemini-3.8-flash` Free Tier 일일 제한(20건) 초과 시 기본 3회 재시도로 인해 Vercel Serverless Function 504 Timeout 발생.
- **해결**: 호출 시 `maxRetries: 0`을 지정하여 쿼터 초과 시 0.5초 만에 즉시 `gemini-3.6-flash` 및 `gemini-3.1-flash-lite`로 인계되는 4단계 Fallback 풀을 구축하여 무중단 서비스 실현.

## 6장. 회고 & 향후 로드맵

### 1. 배운 점 및 핵심 교훈
- **"LLM을 맹신하지 말고 시스템 아키텍처로 통제하라"**:
  - LLM은 자연어 문맥 해석과 유연한 이해에 뛰어나지만, 정량 계산이나 누락 방지에는 취약합니다.
  - **개인정보 가림(정규식) + 숫자 기준 계산(Rule Engine) + 조문 번들링 + 원문 인용 검증(Repair)**의 시스템적 가드레일이 결합되어야만 비로소 실전 서비스 수준의 신뢰도를 확보할 수 있음을 체감했습니다.

### 2. 향후 발전 로드맵
1. **공공데이터포털 부동산 등기부등본 실시간 열람 API 연동**:
   - 특약뿐만 아니라 집주인의 근저당권, 압류, 선순위 채권을 실시간 조회하여 보증금 안전율 자동 산출.
2. **전자서약서 플랫폼 생태계 연계**:
   - 당근마켓 직거래 부동산, 다방, 직방 등 청년들이 많이 쓰는 직거래 플랫폼에 브라우저 확장 및 API 플러그인 제공.
3. **판례 기반 대안 문구 자동 튜닝**:
   - 대법원 판례 데이터를 추가 임베딩하여 분쟁 발생 시 세입자에게 100% 승소 판결이 내려진 검증된 대안 특약 문구 자동 추천.
