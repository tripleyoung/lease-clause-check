# 계약서 특약 점검기 설계 (1차 프로젝트)

> 2026-11-02 변경: 점검 엔진은 계약 종류와 무관하게 두고, 점검 기준을 '점검팩'으로 끼운다. 이번 제출은 임대차 특약 팩과 헬스장·PT 환불 팩 2개. 위험 항목마다 수정 요구 대안 문구를 준다. 신호등(보호됨=초록, 언급 없음=노랑, 위험=빨강)으로 표시한다.

## 1. 무엇을, 왜

첫 자취를 준비하는 사회초년생(같은 반 동기들)이 전월세 계약 직전에 받은 **특약 문구**에서 돈을 잃을 수 있는 조항을 놓친다. 계약서는 처음 보고, 무엇을 봐야 하는지 모르고, ChatGPT에 붙여 넣으면 답이 매번 다르고 무엇을 빠뜨렸는지 알 수 없다. 개인정보(주민번호·주소·계좌)도 그대로 외부로 나간다.

이 도구는 특약 문구를 붙여 넣으면 **정해진 점검 항목을 하나도 빼지 않고** 항목마다 있음·없음·위험을 표시하고, 경고마다 **공개 근거 문서의 위치를 인용**한다. 법률 판단이 아니라 "계약 전에 무엇을 확인·요구할지"를 알려 준다.

시장 배경: 2026년 임대차 거래의 약 62%가 월세(1~7월 전국, 국토부 실거래 집계 보도)라서 전세만이 아니라 전세·반전세·월세 계약을 모두 다룬다.

## 2. 목표 · 하지 않을 것 · 실패로 보는 것

**목표**
- 핵심 흐름 하나가 끝까지 돈다: 특약 붙여 넣기(계약 종류 선택) → 개인정보 가림 미리보기 → 점검 결과(항목별 신호등 + 근거 + 상대에게 물어볼 질문 + 수정 요구 대안 문구).
- 같은 정답 표로 **v0(그냥 ChatGPT식 프롬프트) → v1 → v2**를 비교한 숫자가 있다.
- 막는 장면 4개 이상을 시연한다: 개인정보 가림, 빈·무관한 입력, 너무 긴 입력, API 실패·키 없음.
- README만 보고 다른 사람이 자기 API 키(OpenAI 또는 Gemini 무료 등급)로 실행한다. 배포 주소가 있다.

**하지 않을 것**
- 로그인, DB, 파일(PDF·사진) 업로드와 OCR. 텍스트 붙여 넣기만 받는다.
- 등기부등본 근저당 계산(보증금 대비 위험 비율)은 **시간이 남을 때만** 넣는 추가 기능이다.
- 계약서 전체 조항 해석. 특약만 본다.

**실패로 보는 것 (돌아가도 실패)**
- "이 계약은 안전합니다/위험합니다"처럼 법률 판단을 단정한다.
- 근거 문서 인용 없이 경고한다.
- 실제 개인 계약서 데이터를 시험 자료나 레포에 넣는다.
- 개인정보가 가려지지 않은 채 API로 나간다.
- 점검 항목 중 하나라도 결과에서 빠진다(있음·없음·위험 중 하나는 반드시 표시).

## 3. 정해진 것

- **스택**: 다온 사주 AI(`monorepo/apps/saju-ai`)와 같은 구성(2026-11-02 사용자 결정: Streamlit 안 쓰고 Vercel 배포). React + Vite + TypeScript 화면, Vercel 함수 `api/*.ts`가 `server/*.ts` 처리기로 넘김, Vercel AI SDK(`LLM_PROVIDER` gemini | openai, 키는 서버 환경 변수만), 근거 문서는 다온의 사주 위키처럼 `knowledge/*.md`로 두고 AI가 도구로 열어 절 단위로 인용. 가이드의 'HTML 바이브 코딩, 키 필요한 API(.env)'에 해당한다.
- **근거 문서**: 국토교통부 주택임대차표준계약서, 국토부·HUG의 전세사기 예방 안내 등 공개 자료만. 점검 항목마다 근거 문서 이름과 위치(조·항 또는 안내 항목)를 저장한다.
- **점검팩 구조**: 팩 하나 = 계약 종류 이름 + 점검 항목 목록 + 각 항목의 근거(문서·위치·URL) + 수정 요구 대안 문구. 엔진(입력 검사·가림·규칙·LLM·보정)은 팩을 받아서 돌 뿐 계약 종류를 모른다. 팩이 없는 계약서는 '점검 기준이 없는 종류라 참고용'으로 표시하고 평가에서 뺀다.
- **헬스장·PT 환불 팩**: 공정거래위원회 표준약관(체육시설 이용 관련)과 소비자분쟁해결기준(체력단련장업)의 환불·위약금·양도·휴회·중도 해지 기준. 숫자 기준(위약금 상한 등)은 규칙으로 계산한다. 항목 6~8개.
- **임대차 특약 팩 점검 항목**: 10~12개. 예) 잔금 전후 근저당 설정 금지, 보증금 반환 시기·방법, 전입신고·확정일자 협조, 선순위 권리·체납 고지, 보증보험 가입 불가 시 계약 해제, 원상복구 범위, 관리비 항목·금액, 중도 해지 위약금, 수리 책임, 집주인 변경 시 고지. 최종 목록과 근거는 빌더가 공개 자료를 읽고 확정한다.
- **시험 자료**: 직접 만든 세트 30건(임대차 18: 전세 6·반전세·월세 12, 헬스장·PT 12). 조정용 10건(임대차 6, 헬스장 4)과 시험용 20건(임대차 12, 헬스장 8). 각 세트에 항목별 정답(있음·없음·위험)을 붙인다. 까다로운 경우를 넣는다: 부정문("설정하지 않는다"), 비슷한 표현, 위험이 하나도 없는 세트, 여러 위험이 섞인 세트, 개인정보가 들어 있는 세트.
- **지표 (개발 직군)**: 위험 항목 재현율(놓친 위험 수)과 정밀도(엉뚱한 경고 수), 항목 누락 0건 여부, 응답 시간. 버전별로 같은 30건에 돌려 표로 낸다.
  - v0: "다음 특약에서 위험한 조항을 찾아 줘" 한 줄 프롬프트
  - v1: 점검 항목 목록 + 항목별 JSON 출력 + 근거 인용 강제
  - v2: 규칙 검사(키워드·정규식) 결과를 함께 주고, 모델 출력을 규칙으로 다시 확인(항목 누락·근거 없는 경고 걸러 내기)
- **개인정보 가림**: 주민번호, 전화번호, 계좌번호, 상세 주소(동·호수)를 정규식으로 API 호출 **전에** 가리고, 가린 결과를 화면에 먼저 보여 준다.
- **제출물**: GitHub 주소, README, `프롬프트.md`(버전별 프롬프트와 바꾼 이유, AI 실수를 잡은 사례), 발표 자료(가이드의 6장 구성, 개발 직군: 구조·오류 처리·프롬프트 버전 비교), 배포 주소, 시연 영상 1~3분(핵심 흐름 + 막는 장면).

### 3.1 판정과 채점 (설계자 결정, 빌더 검토 반영)

- **항목 판정 3가지**: `보호됨`(세입자를 지키는 조항이 있음) · `언급 없음`(관련 조항이 없어 계약 전에 확인·요구할 것) · `위험`(세입자에게 불리한 조항이 있음). 모든 항목이 셋 중 하나로 나와야 한다.
- **채점 단위는 항목**: 30건 × 점검 항목 수. 주 지표는 `위험` 판정의 재현율(놓친 위험)과 정밀도(엉뚱한 위험 경고), 보조 지표는 항목 누락 수와 3가지 판정 전체 정확도, 응답 시간.
- **자기 채점 막기**: 정답 표는 규칙·프롬프트를 쓰기 **전에** 만들고 커밋해 봉인한다. 30건을 개발용 10건(프롬프트·규칙 조정에만 씀)과 시험용 20건(최종 숫자만 냄)으로 나누고, 발표 숫자는 시험용 20건으로만 낸다. 정답은 사람이 쓴다(LLM이 만든 문장은 쓸 수 있어도 정답 판정은 사람).
- **근거 인용 검증**: 표준계약서·안내 문서를 실제로 열어 읽고 확인한 조·항만 쓴다. 기억에 의존한 조항 번호는 쓰지 않는다(읽는 시간 30분 예산).

## 4. 빌더에게 맡기는 것

- 화면 배치와 문구(해요체, 과장 없이), 결과 표 모양.
- 점검 항목의 최종 목록과 근거 위치(공개 자료를 직접 읽고 정한다).
- 정규식 세부, JSON 스키마, 평가 스크립트 구조.
- 모델 기본값(쓸 수 있는 OpenAI 모델 중 싸고 빠른 것).
- 시연 영상 녹화 방식(실제 화면 녹화, 자막으로 막는 장면 표시).
